# JevBridge 像素桥协议 v1

> 仅用于本地自建的 AzerothCore 3.3.5a 服务器上的研究实验。

WoW 插件 `addon/JevBridge` 把游戏状态编码成客户区左上角的一条色块；Windows 侧的 `capture/JevCapture.exe` 截屏、解码、校验，输出 JSON。像素桥只做感知，不做决策，也不碰键鼠。

字段的唯一来源是 `protocol/schema_v1.json`；插件用的 `SchemaV1.lua` 由 `tools/gen_schema_lua.py` 生成（去掉 doc），测试会检查它是否最新。

## 1. 载荷

- 字段按 schema 顺序定长排列，整数一律大端。当前载荷 **263 字节**。
- 数值：非数字或 NaN 记 0；按 `floor(v + 0.5)` 四舍五入；截到 `[0, 类型最大值]`。
- `bits8` / `bits16`：第 k 个名字对应第 k 位（最低位是第 0 位）。
- `array`：固定 `count` 项，缺的项全部记 0。
- `caps` 记录客户端实际提供了哪些接口；某一位为 0 时，相关字段恒为 0，**不代表真值为 0**。

### 法术名哈希

3.3.5a 的 `UnitCastingInfo` / `UnitChannelInfo` 不返回法术 ID，所以用名字哈希：

```
h = 0
for 每个 UTF-8 字节 b: h = (h * 31 + b) mod 2^24
空串 → 0；结果为 0 时记作 1
```

## 2. 帧

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 1 | magic `0x4A`（'J'） |
| 1 | 1 | version `1` |
| 2 | 2 | seq（u16，每次刷新 +1，回绕） |
| 4 | 2 | len（载荷字节数） |
| 6 | len | 载荷 |
| 6+len | 2 | CRC16 |

CRC：CRC-16/CCITT-FALSE，多项式 0x1021，初值 0xFFFF，不反射，无最终异或，覆盖 header + 载荷。校验向量：`"123456789"` → `0x29B1`。

整帧 271 字节。

## 3. 色块

- 每格 3×3 物理像素（`/jevbridge px` 可改），每行 128 格，行优先。
- 第 0 行开头 8 个**同步格**，白黑交替（白、黑、白……）。
- 其后每格装 3 个半字节：R、G、B 各一个，按字节的高半字节在前依次排列，末尾补 0。
- 每通道 16 档，第 n 档的值为 `n × 17`（0、17、…、255）。解码取 `round(v / 17)`，每通道偏差在 ±8 以内都能还原。
- v1 一帧：8 + ⌈271×2/3⌉ = **189 格**，占 2 行（128 + 61）。3 像素时色条为 384×6 像素。

插件把框体挂在 `WorldFrame` 下（Alt+Z 隐藏界面时仍可见），每格边长 `cellPx × 768 / 客户区物理高度 / 有效缩放` 个 UI 单位，使每格正好落在整数物理像素上。客户区高度默认读 `gxResolution`，可用 `/jevbridge height <n>` 覆盖。默认 30 Hz，只重设颜色变了的格子。

## 4. 解码（JevCapture）

1. **找同步头**：逐行扫描，三通道均值 ≥ 128 判白，切成黑白段。对每个白段起点，连同其后 7 段作为候选；一行里有多个候选时逐个试。
2. **格距**：规格原文是 `(第 8 段起点 − 第 1 段起点) / 7`。实现中改用 `(第 8 段起点 − 第 2 段起点) / 6`：第 1 段左侧可能是亮背景，会和第 1 段粘连，导致其起点不准；第 2–8 段起点都在色条内部。段起点用阈值 128 处的线性插值取亚像素位置。第 2–7 段长度须在格距的 0.55–1.45 倍之间。
3. **行位置**：在 8 个同步格中心各沿竖直方向找同类像素段的上下边界。背景只会让边界向外延伸，所以上边界取最大、下边界取最小，行中心取两者中点。
4. **格距精修**：只用 8 个同步格外推到第 127 格，误差会放大十几倍。因此先读 header 拿到 len，再用第 0 行内部的格边界（相邻像素通道差的加权质心）逐步做最小二乘，修正起点和格距。
5. **采样**：每格只采中心像素，`(x0 + (列 + 0.5) × 格距, 行中心 + 行号 × 格距)` 四舍五入。先验证 8 个同步格的档位是 15/0。
6. **校验**：magic、len（≤ 4096）、CRC。多个候选都失败时，报最接近成功的原因：`crc` > `len` > `magic` > `sync` > `no_sync`。

输出一行 JSON：

| 字段 | 含义 |
|---|---|
| ok / reason | 是否成功；失败原因：`no_sync`、`sync`、`magic`、`len`、`crc`、`capture`、`no_window`、`load: …` |
| seq / ver / len | 帧头；未读到时为 -1 |
| payload | 载荷十六进制；C# 端不解析字段，交给使用方按 schema 解析 |
| pitch / x0 / y0 | 格距、色条左边界、上边界（亚像素，截图坐标） |
| max_err | 各通道离最近档位的最大偏差（≤ 8 才能还原） |
| tick_ms | 截屏时的 `Environment.TickCount` |
| cap_ms / dec_ms | 截屏（或读图）耗时、解码耗时 |

`--image` 模式额外带 `file`。`--live` 只在 seq 变化时输出成功行；失败行在原因变化时立即输出，同一原因每秒最多一行；每 10 秒往 stderr 写一行统计（captures、ok、crc_fail、other_fail、frames、seq_gaps、耗时均值/最大值），用来算 CRC 失败率。

## 5. 抗干扰测试结果（离线）

`tests/test_decode_exe.py`，每项 3 组随机 state：

| 干扰 | 结果 |
|---|---|
| 偏移 (37, 11) | 通过 |
| 每格 4 像素 | 通过 |
| 双线性缩放 1.25× / 1.5× | 通过 |
| 高斯模糊 σ = 0.6 | 通过 |
| 每通道 ±6 均匀噪声 | 通过 |
| gamma 1.05 | 通过 |
| **gamma 1.1** | **预期失败**：`v' = 255·(v/255)^1.1` 在 6 档（102）附近偏差约 8.9，超出 ±8 容差，报 `crc` |
| 随机噪点背景 | 通过 |
| 改坏一个格子 | 必须报 `crc`，通过 |

说明：

- **模糊**用精确的 5×5 高斯核。PIL 的 `GaussianBlur(0.6)` 用盒式模糊近似，拖尾偏重，会把夹在黑格之间的白格中心压到 245（偏差 10），同样会失败。实际截屏不应有模糊。
- **gamma**：请保持显示 gamma 为 1.0，不要用独占全屏（可能截到黑图），用窗口化或无边框窗口。
- 预热后的纯解码耗时约 0.05 ms/帧（`--repeat 200` 平均）；首帧约 6 ms 是 JIT 预热。

## 6. 待有客户端后确认

- `GetPlayerFacing`、`GetUnitSpeed`、`UnitAura` 第 11 个返回值 spellId、`GetCurrentMapAreaID` 是否可用（看 `caps`）。
- `GetTime` 和 `Environment.TickCount` 是否同一个时钟（决定能否用 `t_ms` 和 `tick_ms` 直接算延迟）。
- `gxResolution` 是否等于客户区高度；不等时用 `/jevbridge height`。
- 独占全屏下截屏是否为黑图。
- 真实链路指标：截屏 + 解码 ≤ 5 ms，状态变化到 WSL 拿到 JSON ≤ 60 ms，连跑 1 小时 CRC 失败率 < 0.1%。
